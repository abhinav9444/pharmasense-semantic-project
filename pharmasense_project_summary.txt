PHARMASENSE — PROJECT SUMMARY

WHAT I STARTED WITH
-------------------
I was given a flat DrugBank Lite export from TogoDB and the requirement was to convert it into a proper OWL ontology, RDF knowledge graph and SPARQL query layer.

I first understood how the source data was structured instead of directly writing RDF. The data had useful relationships between drugs, targets, pathways, categories and classifications, so I decided to model those relationships explicitly.

STEP 1 — DATA COLLECTION
------------------------
I scraped DrugBank Lite IDs 1–200 from TogoDB and stored the records in JSON.

I kept the scraper simple and added basic cleaning/retry handling because the source contained HTML, special characters and missing values.

Result: 200 drug records in structured JSON.

STEP 2 — HOW I MODELED THE RDF
------------------------------
I did not want to store everything as plain text.

Main entities:
- Drug
- ProteinTarget
- Pathway
- DrugCategory
- DrugType
- ATCClassification

Main relationships:
Drug → hasTarget → ProteinTarget
Drug → participatesInPathway → Pathway
Drug → hasCategory → DrugCategory
Drug → hasDrugType → DrugType
Drug → hasATCClassification → ATCClassification
ProteinTarget → associatedWithPathway → Pathway

I used separate RDF resources for targets and pathways because this allows SPARQL to follow relationships between entities instead of only searching text fields.

STEP 3 — OWL ONTOLOGY
---------------------
I created `ontology/pharmasense.ttl`.

I added:
- OWL classes and properties
- Domain and range
- rdfs:label and rdfs:comment
- Inverse properties
- A transitive property
- OWL restrictions for inference

For inference:
hasDrugType → BiotechType ⇒ BiotechDrug
hasCategory → Anticoagulants ⇒ AnticoagulantDrug

The aim was to make the ontology define the meaning of the data, not just define names.

STEP 4 — JSON TO RDF/TURTLE
---------------------------
I used RDFLib to convert the JSON records into RDF triples and serialize them as Turtle.

I kept the graph reasonably small and focused on relationships required by the assignment.

Current graph: about 4,000 triples from 200 records.

The focus was accuracy and useful relationships, not maximum scale.

STEP 5 — SPARQL
---------------
I designed the five SPARQL queries from the actual research questions.

For each query I identified:
1. What the question is asking.
2. Which RDF entities are involved.
3. Which relationships connect them.
4. Which result columns are actually useful.

The five queries are:
1. Shared protein target with Lepirudin
2. Drug pairs sharing more than 3 pathways
3. Thrombin mechanism with non-B01 ATC code
4. Bleeding toxicity with more than one category
5. Drugs inferred as both BiotechDrug and AnticoagulantDrug

Each query was tested separately and the outputs were stored in `query_results/`.

CHALLENGES I FACED
------------------

1. RDF DATA CLEANING
Problem:
Source values contained HTML, special characters and inconsistent missing-value text.

Fix:
Added cleaning and URI normalization before creating RDF resources.

2. OWL REASONING FAILED INITIALLY
Problem:
BiotechDrug and AnticoagulantDrug were not being inferred.

What I checked:
The explicit `hasDrugType` and `hasCategory` facts existed, but the ontology did not yet define the required equivalence restrictions.

Fix:
Added OWL restrictions and verified the result again with OWL-RL.

3. SPARQL PREFIX ERROR
Problem:
When the five queries were loaded separately, the `pharma` prefix was lost and Query 5 failed.

Fix:
Preserved the PREFIX declarations while loading the queries.

4. QUERY 2 RETURNED NO RESULTS AFTER REDUCTION
Problem:
The graph had been reduced too aggressively and important pathway relationships were removed.

What I did:
Checked the RDF instead of adding artificial triples.

Fix:
Retained the required source pathway information and modeled:
Drug → hasTarget → ProteinTarget → associatedWithPathway → Pathway

Result:
Query 2 produced genuine shared-pathway results.

5. QUERY 1 RETURNED IRRELEVANT ROWS
Problem:
The first version allowed unrelated drugs with empty target values to appear.

Fix:
Made target, gene and function relationships mandatory so only genuine shared-target matches are returned.

6. SEMANTIC LAYER CLASSIFICATION ISSUE
Problem:
A custom ATC question was incorrectly treated as one of the five fixed queries.

Fix:
Used direct matching for the five validated assignment questions. Other questions use the custom-query path.

7. GEMMA DID NOT ALWAYS RETURN CLEAN SPARQL
Problem:
Gemma sometimes returned explanation or extra text instead of a query.

Fix:
Added query extraction/retry logic and restricted execution to read-only SELECT/ASK queries.

WHY I CHOSE THIS APPROACH
-------------------------
My main focus was accuracy rather than scale.

I avoided:
- adding fake triples just to make a query return results
- keeping unnecessary relationships only to increase triple count
- using the LLM to rewrite queries that were already validated
- making the graph larger without a clear modelling/query reason

The five assignment questions use validated SPARQL directly.

For other questions, local Gemma is used only for natural-language understanding and custom SPARQL generation.

VALIDATION I DID
----------------
I separated validation into small steps so failures could be traced to the correct layer.

`validate_ontology.py`
→ checks that the ontology parses.

`verify_graph.py`
→ checks the generated RDF graph and important relationships.

`test_reasoning.py`
→ checks OWL inference.

`run_all_queries.py`
→ executes all five SPARQL queries and stores their results.

`semantic_layer.py`
→ checks the natural-language → SPARQL → RDF result flow.

MAIN LEARNING
-------------
The main thing I learned from this project is that a good knowledge graph is mainly about correct modelling.

The number of triples is not the main goal.

The important part is choosing the right entities, defining meaningful relationships, keeping identifiers consistent, writing queries that match the model, validating each stage, and checking failures instead of hiding them.

That was the approach I followed while building PharmaSense.
